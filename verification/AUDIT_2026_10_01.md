## Judgment

Keep the core idea, fix the trustworthiness of its gates, and reduce the planned
scope until real projects demonstrate which additions help.

The harness is a useful engineering baseline for projects developed with coding
agents. It gives humans and agents consistent commands, places to record
decisions, and a shared expectation of observable verification. Those are
credible mechanisms for reducing repeated explanations and preventable errors.

It has not demonstrated a material improvement in project outcomes. Its tests
measure parts of the command/configuration implementation; they do not measure
whether agents produce better software with this harness. Two reproduced cases
also allow the test command to succeed while application tests are failing.
That undermines its most important promise: trustworthy evidence of completion.

The right positioning is a small project engineering layer used with an agent
runtime. This repository does not implement the model/tool loop, sandbox,
permission enforcement, resumable execution, or agent evaluation. There is no
need to build those here unless a specific project requires them.

## Reproduced findings

P1 means fix before treating the command as a reliable project gate. P2 means a
concrete compatibility or correctness problem to fix before broader adoption.
All findings have high confidence in the described code behaviour. For F3, the
wrong classification was executed and verified; the absent shell tools were
not run.

### F1 — P1: installed Python projects run harness tests before application tests

**Location:** `.harness/bin/test`, lines 13–17.

When a project has the shipped `.harness/tests` directory and root dispatcher,
with no explicit test override or Node test script, the command selects harness
contract tests before considering the application's `tests/` directory.

**Reproduction:** copy the actual 54 managed files plus config/manifest to a
temporary directory and add an application unittest that fails. The copied
`./harness test` exits 0 with 14 passing harness tests. Direct application test
discovery exits 1 with the intended failure.

**Impact:** a project created from this starter can receive a green test result
without running its application tests.

**Why existing tests miss it:** they verify harness self-testing and command
overrides, not a fully installed harness coexisting with failing project tests.

**Fix:** put harness tests behind `self-test`, or configure them explicitly for
this repository. Resolve application tests independently. Add a regression with
both suites present and a failing application assertion.

### F2 — P1: missing pytest silently changes which tests execute

**Location:** `.harness/bin/test`, lines 19–24.

If pytest is unavailable, the command automatically switches to unittest.
Unittest does not execute ordinary pytest-style module-level test functions.

**Reproduction:** in a temporary virtual environment without pytest, create one
passing unittest and one module-level test containing a failing assertion.
`harness test` exits 0 after running only the unittest. Executing the skipped
test function directly exits 1.

**Important boundary:** Python 3.14 correctly rejects the entirely empty
discovery case: the all-pytest-function probe produces `NO TESTS RAN`, with
underlying exit 5 normalised to harness exit 1. The false success reproduced
here requires a mixed suite; this report does not claim the empty-run case
passes on the tested runtime.

**Impact:** environment changes can silently remove coverage while preserving a
green result.

**Why existing tests miss it:** the Python fixture uses unittest only and does
not exercise a missing declared pytest dependency or mixed suite.

**Fix:** use an explicit project test runner. If the declared runner is missing,
fail with setup instructions. Do not infer an equivalent runner from whatever
happens to be installed. Record test collection/count where supported.

### F3 — P2: executable Python checks are classified as shell

**Location:** `.harness/checks/standards/check`, lines 65–84 and 157–169.

Every extensionless executable is assigned the shell profile. All five policy
check executables have Python shebangs, yet `profile_for` returns `shell` for
each. Those paths enter the ShellCheck/shfmt argument list when the tools exist.

**Impact:** installing the recommended tools exposes invalid language routing,
and extensionless Python sources miss Python-aware size analysis. The current
green result masks this because both shell tools are absent.

**Why existing tests miss it:** profile tests cover `.py` and Markdown suffixes,
not executable shebangs or a complete tool environment.

**Fix:** inspect supported shebangs for extensionless files, use explicit
configured paths where ambiguous, and share the same classifier between
profile selection and tool routing. Verify with real installed tools in CI.

### F4 — P2: exclusions do not have consistent path semantics

**Locations:** `.harness/checks/standards/check`, lines 38–49;
`.harness/checks/documentation/check`, lines 8–13;
`.harness/checks/demo-integrity/check`, lines 7–15;
`.harness/bin/check`, lines 65–69.

Standards compares individual path components with configured exclusion strings.
An accepted exclusion such as `src/generated` cannot match those components.
Documentation, demo-integrity, and Python syntax fallback use separate hardcoded
lists instead of the validated configuration.

**Reproduction:** `src/generated/large.py` still produces a size warning with
`src/generated` excluded. A broken link under the default excluded `generated/`
directory makes the public check exit 1.

**Impact:** declared exclusions can be ineffective, and one gate can block on
content another gate deliberately excludes. All these scanners also traverse
the tree before filtering; dependency-heavy repositories need a pruning
strategy, although performance at that scale was not benchmarked here.

**Why existing tests miss it:** the exclusion test covers a single directory
name and only the standards check.

**Fix:** define root-relative directory/pattern semantics once and reuse a
pruning file walker across harness-owned checks. Leave native tool exclusions
authoritative for their own scope, and document that boundary explicitly.

### F5 — P2: explicit check overrides still run automatic Python checks

**Location:** `.harness/bin/check`, lines 33–51.

After a configured or CLI check command finishes, Python detection runs
unconditionally. This differs from the documented precedence and the early
return used by setup overrides.

**Reproduction:** a temporary Python project with `--command true` successfully
runs that command, then fails the additional automatic syntax scan.

**Impact:** a project cannot fully delegate static checking to its selected
environment and scope. Tools may run twice, or the extra scan may inspect files
the authoritative project command deliberately excludes.

**Why existing tests miss it:** command-precedence tests exercise `test`, not
`check`, and no case combines an override with a Python manifest.

**Fix:** keep policy checks mandatory as configured, but choose one resolved
project-check implementation. Make any additional automatic stages explicit.

### F6 — P2: project-specific skills become unexpected managed files

**Location:** `.harness/bin/manifest.py`, lines 19 and 47–63.

The manifest enumerates every file under `.agents/skills`, although the documented
ownership boundary covers shipped skills and allows project additions.

**Reproduction:** a copied installation verifies successfully; adding a separate
project-specific skill makes verification exit 5 with an unrecorded-managed-file
error. `inspect` uses that verifier.

**Impact:** ordinary skill customisation makes a healthy installation appear
broken. Regenerating the manifest would instead classify project content as
harness-owned, a dangerous basis for the planned updater.

**Why existing tests miss it:** they check modified shipped files and relative
paths, not additional project-owned skills.

**Fix:** track a release-owned file inventory or explicit shipped skill names;
do not infer ownership from the entire skills directory.

### F7 — P2: fixture virtual environments invalidate the manifest

**Location:** `.harness/bin/manifest.py`, lines 20–31.

The manifest ignores `node_modules` and several caches but does not ignore
`.venv`. The documented Python setup creates a `.venv` in the target directory,
including when the target is the bundled fixture under `.harness/`.

**Reproduction:** create a real temporary virtual environment without pip in the
copied Python fixture. Manifest verification changes from exit 0 to exit 5,
identifying `.venv/bin/Activate.ps1` as an unrecorded managed file. No network or
package installation is needed to reproduce this.

**Impact:** normal local setup can break inspection and the installed-manifest
contract test. Manifest generation can also absorb machine-specific generated
environment files.

**Why existing tests miss it:** they assert that `node_modules` is absent, but
do not create a Python environment under a managed fixture.

**Fix:** exclude runtime environments and generated state, preferably by deriving
the inventory from release inputs rather than walking everything on disk.

## Capability gaps and misleading confidence

These are separate from implementation defects. Several are explicitly planned
for later phases; the problem is treating current output as stronger evidence
than it provides.

| Area | Current behaviour | Required interpretation or improvement |
| --- | --- | --- |
| Context | Product, design, data, and security are still templates | Useful prompts, not project knowledge |
| Architecture check | Checks filenames and three headings | Rename/report as context structure; add native dependency rules only where needed |
| Provenance check | Searches for five strings in `DATA.md` | Does not verify any output against a source |
| Demo integrity | Looks for a few claims, then two words in data context | A warning heuristic, not evidence an integration works |
| Tool coverage | Missing tools warn and return success | Report `pass`, `fail`, `skipped`, `unavailable`; require selected tools in strict CI |
| Readiness configuration | Keys validate and print but do not control checks | Make reserved status obvious or implement them |
| Security mode | `off`, `local`, and `ci` validate but do not select security checks | Do not imply a security scan ran |
| Shared line width | Printed by standards; native config remains authoritative | It is not a global formatter setting that changes all tools |
| CI | No workflow present | Required checks currently depend on local execution and agent compliance |
| Evaluation | 14 deterministic harness tests | No measured agent/task improvement, cost, or human-review reduction |
| Installation/update | Roadmap only | Existing-repository adoption and safe upgrades remain unverified |
| Runtime safety | Written approval rules, ordinary shell command execution | Actual isolation, credentials, and approvals belong to the executing runtime |

The fault probe sets `fail_on_needs_input = true`, adds an absent required
document, and selects security mode `ci`. The public check still exits 0 with
the templates present. This is consistent with deferred implementation, but
these settings should visibly say they are inactive.

Checksums are useful for accidental drift and future merge decisions. They are
not a security boundary when the executing agent can also edit the manifest and
checks. Critical CI configuration, credentials, and approval enforcement need
independent controls. Ordinary repository instructions cannot provide those.

## Would it materially improve projects?

**Plausible, especially for repeated work across small projects; unproven here.**
The assessment below is an inference from mechanisms and the reviewed code,
not a measured productivity result.

| Project situation | Likely value | Main condition |
| --- | --- | --- |
| Prototype revisited across many sessions | Better continuity, fewer repeated explanations, explicit simulated behaviour | Context must be brief, accurate, and maintained |
| Small project with weak or inconsistent checks | Potentially substantial reduction in preventable regressions | Fix test routing and make tool coverage dependable |
| Established repository with good CI and native conventions | Mainly a common entry point and selective context | Adapt to existing tooling; avoid a second competing policy system |
| Disposable experiment or tiny copy change | Limited benefit from the full workflow | Use only relevant checks and avoid compulsory plan/task/report ceremony |
| Production service | Helpful supporting layer | Security, operational readiness, release and rollback controls need actual implementation |

The net value is avoided rework, review effort, and repeated context-setting,
minus setup, documentation maintenance, extra checks, tokens, and waiting time.
Counting documents, passing checks, lines generated, or tasks closed does not
establish that net value.

The current read burden is measurable: 570 words in `AGENTS.md`, 894 in shared
standards, 123 in the Python profile, 1,297 across canonical context, and
4,634 in
the active plan. Those are word counts, not token or latency estimates. Relevant
context is already partly conditional, but source edits still require all four
standards documents, and the active roadmap is large for routine work.

Keep useful project facts that an agent cannot cheaply infer: non-obvious
commands, integration truth, product constraints, incompatible patterns,
deployment boundaries, and the reason for unusual decisions. Remove repeated
generic advice when tools or narrower instructions already cover it.

## Current state of the art

Research checked on 1 October 2026. There is no universal best harness. The
strongest common direction is an executable feedback loop with small, relevant
context and evaluation on the tasks the system actually performs.

| Practice and primary source | Evidence and limits | Implication for this repository |
| --- | --- | --- |
| Minimal, task-specific instructions — [OpenAI, 11 September 2026](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) | Current vendor guidance recommends narrow skill triggers, progressive disclosure, and revisiting blanket read/test instructions as models change. It is model-specific advice, not a controlled productivity result. | Keep the root contract concise; route reads by change type; evaluate rules across the models actually used. |
| Test whether context helps — [Gloaguen et al., revised 29 September 2026](https://arxiv.org/abs/2602.11988v3) | Their evaluated settings show no general success improvement from context files and over 20% higher inference cost on average. Non-standard practices can still merit instructions. | Treat every permanent instruction as a hypothesis with a maintenance and execution cost. |
| Check generalisation — [Khatri, July 2026](https://arxiv.org/abs/2607.27250) | A small preprint reports 288 runs over 17 tasks in three repositories and two agents, without a measurable correctness gain from context strategy. Its sample and equivalence bounds limit broad claims. | Do not confuse better repository orientation with better implementation correctness. |
| Evaluate skills end to end — [OpenAI, January 2026](https://developers.openai.com/blog/eval-skills) | Defines outcome, process, style, and efficiency goals, then deterministic and rubric-based evaluation. | Test the five skills by running real tasks; file-presence checks are insufficient. |
| Independent application feedback — [Anthropic, March 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) | A vendor case study uses browser-driven evaluation and task contracts. One full harness run cost $200 versus $9 solo; later model improvements let the author remove orchestration. This is not an equal-budget benchmark. | Add browser/API/persistence evidence where it catches real failures; use separate evaluation selectively and remove overhead that stops helping. |
| Grade outcomes and inspect traces — [Anthropic, January 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | Combines deterministic, model, and human graders; traces expose failure causes that a final success message misses. | Store commands, results, changed revision, and acceptance evidence; use human judgment for product/design quality. |
| Separate runtime responsibilities — [Anthropic, April 2026](https://www.anthropic.com/engineering/managed-agents) | Describes separating the session log, agent loop, and execution environment for recovery and credential isolation. Vendor architecture, not a requirement to build a platform. | Integrate with the agent runtime; keep repository checks portable and independently runnable. |
| Enforce controls at the action boundary — [OpenAI guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) | Tool approvals interrupt execution and carry resumable state; agent-level guardrails do not cover every nested action. | Keep real approval and sandbox controls outside editable prose. |
| Measure delivery, not enthusiasm — [DORA 2025](https://dora.dev/research/2025/dora-report/) and [METR, February 2026](https://metr.org/blog/2026-02-24-uplift-update/) | DORA describes AI as amplifying existing organisational strengths and weaknesses. METR says selection effects make its later productivity estimate unreliable. Neither tests this harness. | Measure accepted work, review time, defects and total effort locally; do not borrow a universal productivity percentage. |

These sources support disciplined experimentation. They do not justify adding
multi-agent orchestration by default, writing more documentation automatically,
or assuming that current frontier models remove the need for independent checks.

## Improvements in priority order

### 1. Make a green result trustworthy

Fix F1–F7 before expanding the feature set. Separate `test` from `self-test`,
require the intended runner, correct file classification, unify harness-owned
path handling, respect command resolution, and define managed ownership from
release inputs.

Add a small result format containing the command, scope, tool/version, exit
status, duration, revision, and evidence location. Distinguish skipped or
unavailable checks from executed passes. Keep local advisory mode available,
while allowing a project's required CI tools to fail closed when missing.

Acceptance: deliberately failing project behaviour always fails the appropriate
gate; required missing tools cannot produce a fully verified result; project
skills and virtual environments do not corrupt installation health.

### 2. Make the smallest complete developer loop work

Add `format` by delegating to project formatters, plus a read-only `doctor` for
runtime and tool availability. Provide a documented way to install the declared
development tools. Python setup currently ignores uv/Poetry locks and does not
install declared development extras; use explicit native commands or supported
lockfile-aware profiles rather than promising universal detection.

Give this repository explicit static and test commands for its own code. Add a
thin macOS CI workflow using the same public commands and complete tooling.
Exercise installed copies, paths with spaces, negative cases, and both fixtures.
Keep slow or irrelevant checks separate from the quick edit loop.

Acceptance: a clean supported environment can reproduce the gate results using
documented commands, including the real linters that were absent in this audit.

### 3. Reduce context and workflow overhead

Keep `AGENTS.md` as a short contract and routing map. Direct architectural edits
to architecture context, data changes to data context, and releases to security
and deployment requirements. Let native configuration carry formatting rules.

Use a task/plan for work with meaningful scope, uncertainty, or coordination.
Allow a small reversible edit to use concise acceptance evidence without
creating several new documents. Retain product truth and provenance, which are
particularly valuable in demonstrable prototypes.

Separate reusable starter templates from this harness project's own context.
Fill the harness's product/security facts from actual implementation and clearly
mark future capabilities. Split the long roadmap into a short active task plus
linked proposed work; avoid repeatedly loading every future phase.

Acceptance: routine edits retrieve only relevant context, and no placeholder
document can be mistaken for a confirmed project fact.

### 4. Prove value on real projects before building a distribution platform

Bring dogfooding and evaluation forward from Phase 10. Run a bounded pilot on
three representative repositories: an actual web application, a Python project,
and a mature repository with established tooling.

Start with approximately 15–20 representative tasks, including a bug, bounded
feature, refactor, UI interaction, and a resumed session. Use matched starting
revisions, the same model/version and budget, isolated workspaces, and repeated
trials where feasible. Treat this as a pilot, not a statistically conclusive
benchmark.

Compare three conditions: existing project conventions, the proposed lean
harness, and the full current workflow. Hold independent acceptance tests and
review criteria constant. The baseline must retain existing CI and tests;
otherwise the comparison rewards basic engineering rather than this harness.

| Measure | How to assess it |
| --- | --- |
| Accepted task success | Independent behaviour tests plus reviewer acceptance |
| Human effort | Active implementation, review, correction, and context-setting time |
| Agent effort | Elapsed time, tool calls, token/cost data when available |
| Reliability | Regressions, missed requirements, reopened work, false success claims |
| Continuity | Time and accuracy when a fresh session resumes the same project |
| Harness burden | Setup time, document maintenance, irrelevant reads/checks |

Set the adoption threshold before running the pilot. For example, a 15–20%
reduction in median human effort with no observed quality regression could be a
useful business threshold; this is a proposed decision rule, not a forecast or
research finding. Report uncertainty and task-level failures, then expand the
sample if the result is close. Repeat key evaluations when the model or harness
changes substantially.

### 5. Add installation, governance, and updates only as demand appears

Once real adoption reveals repeated friction, implement a small dry-run/merge
workflow that preserves existing project files. Add update machinery when
multiple installations need it. Use existing scanner and suppression formats
before inventing a central exception engine.

The current ten-phase plan correctly notices real future problems, but places
dogfooding and CI too late. The next milestone should be a reliable, measured
loop on real projects. Safe distribution can follow evidence of reuse.
