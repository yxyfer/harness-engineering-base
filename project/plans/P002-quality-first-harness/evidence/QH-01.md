## Synthetic application contract

Use only generated identities and disposable storage. No customer/model service
participates. Each case resets to the same seed and verifies stored values
through an independent connection/process, rather than the save response alone.

These are bounded reference-app assumptions for Steps 10-15. The Next.js app
lists, edits and saves work items. The Python example validates and atomically
imports the same small domain through a CLI; it does not add a Python web app.

- Tenant `north`: editor `alex`, viewer `sam`, editor `jamie`.
- Tenant `south`: editor `lee`. Accounts/sessions are local synthetic fixtures.
- Item `W-001`: tenant `north`, owner `alex`, title `Prepare brief`, status
  `draft`. Item `W-002`: tenant `north`, owner `jamie`, title `Review copy`,
  status `ready`. Item `W-003`: tenant `south`, owner `lee`, title `Check pack`,
  status `draft`.
- Only an authenticated editor in the item's tenant who owns it may edit.
  Viewers may read their tenant's list. Foreign-tenant rows are never listed.
- Titles are trimmed, nonempty, and at most 80 Unicode code points. Status is
  exactly `draft` or `ready`. IDs remain unchanged. Titles are plain text.
- Python import uses UTF-8 CSV with exactly `id,title,status` headers and unique
  nonempty IDs. Its local store has no accounts/tenants. The title/status rules
  are identical; batch duplicates and collisions with existing IDs are errors.
- A successful save/import commits all intended state. Validation or storage
  failure commits none. A save failure preserves the user's pending input.
